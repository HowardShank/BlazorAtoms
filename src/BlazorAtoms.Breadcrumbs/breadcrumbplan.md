# Breadcrumb Capability — Design Plan

## Context

BlazorAtoms needs a breadcrumb component covering both static (declared page hierarchy) and dynamic (runtime nav-driven) breadcrumb trails, per the Navigation Components roadmap item. Two candidate mechanisms were raised — a static `[AtomBreadcrumb]` page attribute, and a dynamic management service driven by `NavigationManager`/route data — and this plan resolves them into one hybrid architecture rather than picking one. Design was refined over several rounds of Q&A; decisions below are locked, not open. Per explicit instruction, no existing Breadcrumb-named code/folder in this repo was scanned or read while producing this plan — conventions were sourced from other libraries (`BlazorAtoms.Navigation`, `.Highlights`, `.Inputs`) instead. `BlazorAtoms.Breadcrumbs` (src + tests) already exists per git history; this plan's implementation phase should reconcile with whatever is already scaffolded there rather than assuming an empty folder.

## Locked design decisions

1. **Static attribute = structure, dynamic service = runtime state + augmentation.** `[AtomBreadcrumb]` on an `@page` component defines a deterministic parent/child route graph (title template, `ParentRoute`, `IsRoot`). This graph is refresh-safe — a direct deep link resolves its full ancestor chain from attribute metadata alone, no click-history required. (No `Order` field — chain order is already fully implied by the `ParentRoute` walk itself; a separate ordering field would be dead weight with no defined consumer.)
2. **Dedup / revisit**: truncate-to-ancestor. Nav pattern A→B→C→A→D collapses to A→D (browser-history-style). This rule applies **only to the dynamic tail** (see decision 6) — static-chain segments recompute fresh on every visit and can never "dupe." Matching identity for "is this the same entry" = **the entry's route URL with the query string stripped** (path only). Two entries with the same path but different query strings are treated as the same node for truncate purposes; two entries with the same display `Title` but different paths are *not* considered the same node.
3. **Root-reset trigger**: precedence is `provider.IsRootRoute predicate ?? page.[AtomBreadcrumb].IsRoot`. Provider-level `Func<string,bool>?` predicate wins if supplied; falls back to the page's own `IsRoot` flag (plain `bool`, not nullable — attribute named arguments can't be `Nullable<T>` per CS0655, and an omitted named argument already defaults to `false`, so no tri-state was actually needed); defaults to non-root.
4. **Attribute is optional — unattributed pages get an automatic URL-derived entry, not silence.** *(Amended post-implementation: originally these pages were invisible unless the page explicitly called `Push`; real-world testing showed that reads as broken — "why doesn't this page show up at all" — so the service now auto-appends a fallback entry titled from the URL's last path segment, e.g. `/customers/482/my-draft` → "My Draft".)* The page can still call `AtomBreadcrumbService.Push(entry)` (or `PushAsync`, see decision 7) — with the **same `Key`** as the auto entry — to replace that placeholder once real data is available (e.g. an entity name), rather than adding a duplicate. A `Push`/`PushAsync` call matching an *existing* dynamic-tail `Key` now replaces that entry's content in place (not just its position) — this also fixed a related bug where truncate-to-ancestor on revisit kept stale content at the matched entry instead of refreshing it.
5. **Trail scope = render-tree position, not route-prefix config.** `AtomBreadcrumbProvider` is a `CascadingValue<AtomBreadcrumbService>` producer (same pattern as `AtomDropzoneGroup`/`AtomCanvasStudio` — no `services.AddX()` DI registration, matching repo-wide convention). Nearest-ancestor cascading semantics decide which provider a page reports to. Nesting a provider inside a section layout gives that section its own independent trail for free; provider mount/unmount (layout swap) naturally tears down its own trail — no cross-scope reset logic needed.
6. **Merge model for mixed nav**: an attributed page's trail is always the fresh static chain (root...current) resolved from the attribute graph. `Push()`-based entries append *after* that static head as a dynamic tail. Truncate/dedup (decision 2) only ever operates on that tail.
7. **Async title resolution is a first-class requirement**, not just nav-timing hygiene. A page may need a title token resolved from an async source (e.g. `Customer.Name` fetched after nav). Design:
   - Every `LocationChanged` event bumps a monotonic generation counter on the service.
   - Async title/token resolution (`SetDataAsync(key, Task<string>)`) and `Push`/attribute-chain rebuilds all capture the generation active at their start.
   - On completion, a result is applied only if the generation still matches current — otherwise it's discarded (stale nav superseded it).
   - The rendering bar shows a per-segment pending/loading state for any token still unresolved, rather than blocking the whole trail.
8. **Attribute discovery = runtime reflection, cached once — but only for the static parent graph, not current-page resolution.** On first `AtomBreadcrumbProvider` init, scan loaded assemblies for `@page` components carrying `[AtomBreadcrumb]`, build a `Type → ParentRoute-template` graph (author-written string-to-string edges, no live URL involved), cache it statically (process-lifetime). Flag as a risk: reflection-based assembly scanning has known AOT/trimming caveats — must be verified against `BlazorWebAppWasmDemo` (published/trimmed build), not just the Server/interactive hosts, before this is considered safe. If trimming breaks it, fallback is `[DynamicDependency]`/linker-descriptor annotations or a source-generator swap later — not needed for first pass unless the WASM trim test fails.
9. **Current-page resolution = cascaded `RouteData`, not independent URL matching.** Deciding *which* attributed page the user is currently on must not re-implement Blazor's route-template matching (parameterized segments, constraints, catch-all) by hand via reflection+regex — that duplicates logic the real `Router` already gets right and risks silent mismatches on non-trivial routes. Instead, the app wraps its `<Router><Found Context="routeData">` content in `<CascadingValue Value="routeData">` (one required, documented app-level integration step), and `AtomBreadcrumbProvider` consumes that cascaded `RouteData` to get `RouteData.PageType` directly — an exact, already-correctly-resolved match, no re-derivation. The provider reacts to this cascaded parameter changing (`OnParametersSet`) as its nav-detection trigger and generation-counter bump, rather than subscribing to `NavigationManager.LocationChanged` directly for that purpose. `NavigationManager.Uri` may still be read incidentally (e.g. to evaluate the `IsRootRoute` predicate, which operates on a route string), but it is no longer the mechanism for resolving the current attributed page.
10. **Cycle guard on the `ParentRoute` walk.** Building the static ancestor chain (decision 1) tracks visited route templates in a set as it walks; hitting an already-visited template (misconfigured `ParentRoute` chain, e.g. A→B→A) is a scan-time configuration error (see decision 11), not a silent infinite loop.
11. **Broken/orphan `ParentRoute` fails fast at scan time.** If an attribute's `ParentRoute` string doesn't match any known attributed page's own route template (typo, moved page), the reflection scan (decision 8) throws immediately with a message naming the offending type and the unresolved `ParentRoute` value — surfaced at app startup / first provider init, not silently degraded to "treat as root" or discovered later as a rendering glitch.
12. **Ancestor entries need real, resolved `Href` values, not just templates.** A static-chain ancestor whose route has parameters (e.g. parent template `/customers/{id}` for a `/customers/{id}/edit` page) isn't a directly-usable URL. Resolution: substitute each `{param}` token in the ancestor's route template using the *current* `RouteData.RouteValues`, matched by parameter name (ancestor params are normally a subset of the current route's params). If a required param isn't present in the current route's values, that entry's `Href` is `null` and it renders non-clickable (plain text/`<span>`, not a link) rather than a broken URL.

## Architecture components

- **`AtomBreadcrumbAttribute`** (static metadata) — `Title` (token-templated string, e.g. `"Customer: {name}"`), `ParentRoute` (nullable string), `IsRoot` (`bool`, default `false` — not nullable, per CS0655). No `Order` (see decision 1). Un-prefixed per repo convention (attribute itself is the public "Atom"-named type; no separate enum files needed here).
- **`AtomBreadcrumbEntry`** (data type) — `Title` (resolved display string, with per-token pending placeholder if unresolved), `Key` (route path with query string stripped, per decision 2 — identity for truncate matching), `Href` (nullable resolved URL per decision 12; `null` renders non-clickable).
- **`AtomBreadcrumbService`** (headless, in `BlazorAtoms.Shared`-style split — inherits nothing special, not a component) — owns current trail (`IReadOnlyList<AtomBreadcrumbEntry>`), generation counter, `SetDataAsync`, `Push`/dedup-truncate logic. Exposes a **public** change event (not just an internal bar-refresh hook) — any consumer can subscribe (e.g. sync `<title>`, fire analytics) without needing `AtomBreadcrumbBar` mounted at all. Instantiated per-provider, not DI-registered.
- **`AtomBreadcrumbProvider`** (component, `CascadingValue<AtomBreadcrumbService>` producer, `IsFixed="true"` per `AtomDropzoneGroup` precedent) — owns one `AtomBreadcrumbService` instance, consumes cascaded `RouteData` (`[CascadingParameter]`, requires the app-level `<Found>`-wrapping integration step from decision 9) and reacts on `OnParametersSet` when it changes, exposes optional `IsRootRoute` predicate parameter (evaluated against `NavigationManager.Uri`), runs the reflection scan (cached statically so repeat instances don't re-scan). **No `IAsyncDisposable`/subscribe-unsubscribe lifecycle needed** — unlike `AtomScrollTo`/`AtomHighlighter`'s JS-interop disposal pattern, there's no `NavigationManager.LocationChanged` event handler to clean up (decision 9 replaced it with a cascaded-parameter reaction); implementation should not add a disposal path that isn't needed.
- **`AtomBreadcrumbBar`** (component, inherits `AtomComponentBase` since it owns a styled root) — `[CascadingParameter] AtomBreadcrumbService`, renders the trail with per-segment loading state for unresolved async tokens (a `LoadingPlaceholder` string parameter, default `"…"`, shown in place of an unresolved token rather than leaving it blank/collapsing layout), standard `CssClass`/`Style` splat support. Accessibility markup: `<nav aria-label="breadcrumb">` wrapping an `<ol>` of entries, `aria-current="page"` on the last (current) entry, separators marked `aria-hidden="true"`.

### Out of scope for v1 (explicitly deferred, not silently dropped)

- **Overflow/collapse UX** for very long trails (e.g. GitHub-style middle "…" collapse behind an expandable control) — a v2 concern.
- **Pages with multiple `@page` directives** (multiple route templates on one component type) — `RouteData.PageType` alone can't disambiguate which literal template matched, so per-template attribute variance isn't supported; v1 assumes one route template per attributed page.
- **Rich title-token templating** — v1 supports simple single/multi `{token}` string-replace only, no format specifiers or conditionals.

## Data flow per navigation

1. Cascaded `RouteData` changes (provider's `OnParametersSet` fires) → `AtomBreadcrumbService` bumps generation, looks up `RouteData.PageType` directly in the cached `Type → ParentRoute` graph — no URL re-matching involved.
2. Root check: predicate (against `NavigationManager.Uri`) ?? attribute.IsRoot ?? false → if true, clear trail before proceeding.
3. If `PageType` is attributed: walk `ParentRoute` chain to build static head (root...current), guarding against cycles (decision 10); resolve any title tokens from prior `SetDataAsync` values, marking unresolved tokens pending; resolve each entry's `Key` (path sans query string) and `Href` (route params substituted from current `RouteData.RouteValues`, or `null` if unresolvable — decision 12).
4. If `PageType` is unattributed: static head stays as whatever the last resolved value was; a URL-derived fallback entry is auto-appended to the dynamic tail (decision 4) via the same truncate-to-ancestor/replace-in-place logic as an explicit `Push`. The page's own later `Push`/`SetDataAsync` calls (typically from `OnInitializedAsync`, running after this) then replace that placeholder in place if they use the same `Key`.
5. Page's `OnInitializedAsync` may call `SetDataAsync(key, task)` for async token resolution; on completion, apply only if generation still current; notify bar to re-render.
